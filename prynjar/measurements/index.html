PRynjar / Measurements

The numbers.
And their limits.

A listing time is not an app-start time. An engine is not a whole desktop process. These are recorded measurements, with the distinction kept visible.

Website evidence snapshot: 26 September 2026. Historical measurements retain their original dates.

01 / Why local git

632 files missing from a complete API response.

On 3 September 2026, the product’s author compared the GitHub files endpoint with local git for home-assistant/core#181088.

One real pull request, three ways to count its files
SourceFiles reportedObservation
Pull-request metadata3,632The changed_files field gave the total.
Files API, fully paged3,000Pagination completed without a truncation warning in the files response.
Local git diff3,632All files listed in 1,354 ms, after fetch.

The API did not return an error. Page 31 was empty and its links led back to page 30. Comparing the returned list with the pull-request metadata exposed the missing 632 files.

GitHub documents the 3,000-file maximum for this endpoint. The timing and observed responses above are the author’s recorded experiment, not a benchmark published by GitHub.

PRynjar reads file content and change listings from git. The platform supplies hosted metadata and conversations when connected. Local listing has no API page cap; memory, disk and large-file safeguards still apply.

The 8 September desktop journey ran on Ubuntu 26.04, a Xeon E5-2690 v3 with eight cores, at build 879ae12. It used the built application, a real WebKitGTK window and a synthetic 8,000-file git change.

The original 800 ms target was not met by the whole cold-open journey. Subsequent journey budgets were set from observed behaviour, around 6.6 seconds cold. Component timings remain build gates; whole journeys are recorded separately.

Hardware details for the September website brief’s 939 ms and 85 MB component snapshots were not supplied. They are shown with that limit, and are not presented as measurements from the desktop run.

The gate snapshot supplied on 26 September reports 1,236 C# tests, 389 TypeScript tests and 247 Chromium layout checks. Those checks do not establish that every workflow has been verified on every platform, or by an independent user.

03 / The trust boundary

Your files, index and branches stay yours.

An architecture test refuses thirteen mutating git verbs as argument literals in the engine. A violation fails the build:

stash  checkout  switch  restore  reset  clean
rebase  merge  commit  push  gc  prune  filter-branch

Ref writes outside refs/prynjar/* are refused before git runs. PRynjar can keep its own snapshot refs in that namespace so a review can resume later. “Read-only” describes your working files, index and branches; it does not mean the tool writes no data anywhere.

Drafts and marks live in a SQLite store outside the reviewed working tree. Already-fetched content and cached hosted metadata can be reopened offline; missing content still needs a fetch. Connecting a provider and submitting a review are explicit network operations.

These are engineering controls with tests, not an independent security audit.

04 / Where it honestly stands

Early use, with known gaps.

  • People

    Only the author has used it. A review of the implementation is in progress. External use is the next source of evidence, not something already established.

  • Windows

    The packaged application has been opened on Windows. Builds are unsigned; there is no signing certificate yet.

  • Linux

    The real window and package are exercised under Xvfb. A desktop launcher installation flow is still outstanding.

  • macOS

    Not supported and not planned.

  • Enterprise GitHub

    Support for *.ghe.com exists in code. No enterprise tenant has been available for a real test.

  • Menu keyboard access

    Menu titles take focus but do not currently open from the keyboard. A pointer opens them; each menu command has its own binding. The defect is recorded.

  • Large cold opens

    The 8,000-file journey took 6,636 ms in the recorded test. The original 800 ms target was not met.
